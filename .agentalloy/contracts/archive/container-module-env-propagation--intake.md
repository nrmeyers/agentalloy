# container-module-env-propagation

## What the user actually wants

Container-deploy users must be able to enable the code-index module through the
normal product surface (setup wizard / write-env), and `agentalloy upgrade`
must not silently strand them on a config that predates new modules. Found
live on the user's own install: upgraded to v6.1.2, wired the repo, zero
mention of code indexing anywhere.

## Root cause (verified live, 2026-07-06)

Three layers, worst last:

1. `upgrade` preserves the existing `.env`; `CODE_INDEX_ENABLED` defaults off
   and nothing ever mentions the new module exists. (UX gap.)
2. With the module disabled, `wire` correctly skips the wire-index offer and
   the proxy gate correctly excludes `sys-code-index`. (Working as designed —
   the silence downstream is a consequence of layer 1/3, not a bug itself.)
3. **The bug:** `container_runtime.py` builds the `podman run` `-e` list from a
   hardcoded dict (`AGENTALLOY_PACKS`, `DUCKDB_PATH`, …, `LOG_LEVEL`).
   `COMPOSE_ENABLED`/`CODE_INDEX_ENABLED` are never passed, and the host
   `~/.config/agentalloy/.env` is neither mounted nor read by the container.
   So on container deploys, even a fresh `agentalloy setup` picking "Both" is
   inert: the selection lands in the host `.env` (which only the native path
   reads) and the container starts with defaults. Verified against the live
   container's `CreateCommand`.

CI never caught it because the container test passes `-e CODE_INDEX_ENABLED=1`
in its own hand-built run command — it tests the module, not the deploy seam
that launches it.

## Intent signals

- intent: fix-defect (shipped in v6.1.x; blocks the code-index module for the
  entire container deployment class — the recommended deploy)
- artifact_type: fix + small UX addition (upgrade notice, doctor check)
- scope: medium — launch plumbing + state recording + tests; no storage,
  retrieval, or API surface changes
- urgency: high — the flagship v6 feature is unreachable for container users

## Open questions to resolve in spec/design (not decided at intake)

1. **Propagation mechanism.** Options: (a) allowlist-forward just the module
   toggles from the host `.env`/install-state into `-e` flags; (b) pass the
   whole user `.env` via `--env-file`; (c) record the module selection in
   `install-state.json` and render `-e` flags from state. (b) is tempting but
   forwards host-only keys (paths, ports) that would clobber the baked
   container env — the container's DUCKDB_PATH etc. must win. Leaning
   (a)+(c): state records the selection, run-command renders it; decide in
   design with the full env-key inventory.
2. **Recreate-path unification.** `container_runtime` and
   `upgrade._recreate_container` must render the run command from ONE
   function so they can't drift again.
3. **Upgrade notice shape.** Static "this version added module X and your
   config predates it" vs diffing config keys against the new Settings
   defaults. Keep v1 minimal — no interactive prompt mid-upgrade.
4. **Backfill for existing v6.1.x container installs.** Does `upgrade` to the
   fixed version detect-and-carry a host-.env `CODE_INDEX_ENABLED=1` that the
   old recreate dropped, or is re-running setup acceptable? (Affects release
   notes wording either way.)
5. **Watch/data-dir keys.** `CODE_INDEX_WATCH` and `CODE_INDEX_DATA_DIR` ride
   the same seam — decide whether the container honors them (data dir likely
   must stay on the volume; watch may be meaningful). Enumerate in spec.
